# 해사 문서 검색 평가

## 목적과 준비물

저장소 기본 문서의 질문–정답 인용을 이용해 현재 전처리와 BM25 검색을 재현한다. 기존 API·DB·화면을 변경하지 않으며, DB 주소·계정·LLM 키가 필요 없다. 준비물은 Python과 uv, 최초 의존성 설치용 인터넷이다. 설치 후 평가 자체는 네트워크를 호출하지 않는다.

저장소 최상위에서 실행한다.

```powershell
cd backend
uv sync --frozen
uv run python ../scripts/evaluate_retrieval.py --repeats 3
```

기본 결과는 저장소의 `output/retrieval-evaluation/`에 생성된다. `output/`은 Git 제외다. 질문별 진행 상태를 표시하며 실제 검색 함수를 사용한다. 첫 검색은 문서를 분석하고, 이후 같은 내용의 청크 토큰은 크기 제한 메모리에서 재사용한다. 문서 규모와 캐시 수용 여부에 따라 실행 시간이 달라진다. 과거 측정 요약은 [변경 이력](changelog.md)에 남긴다. 이전 실행을 보존하려면 아래처럼 `--output`을 다르게 지정한다.

- `results.md`: 요약, 질문별 결과, 실패·부분 검색과 답 없는 질문 후보 목록, 재현 환경.
- `results.json`: 정답 라벨, 검색 청크 ID·제목·페이지·점수, 반복 시간, 지표, 입력·코드 SHA-256 해시와 패키지 버전.
- `results.csv`: Excel에서 열 수 있는 UTF-8 BOM 질문별 결과.

기본값은 `--top-k 5 --repeats 3`. 출력 위치는 `--output ../output/another-evaluation`로 바꾼다. 측정된 검색 실패는 CLI 오류가 아니므로 종료 코드 0이다. 라벨·원문 해시 오류나 반복 결과 불일치, 실행 중 입력 변경은 오류로 중단한다. 아직 성능 합격 기준을 정하지 않았으므로 CI 품질 통과 판정으로 사용하지 않는다.

## 자료와 라벨

평가셋은 `backend/knowledge/evaluation/maritime-questions.json`이다. 질문 20개 중 16개는 정답 근거가 있고, 4개는 **이 문서 집합만으로 답할 수 없다**. 후자는 실시간 기상·개인 연락처·없는 기종 매뉴얼·개별 선박의 검증된 CII 등급을 묻는다.

원문은 `backend/knowledge/seed.json` 전체다. 국내 법령·USCG 원문, IMO 안내 요약, 용어집, 가상 예제가 섞여 있다. 각 검색 결과에 원문 파일·종류·URL을 남긴다. 요약과 가상 자료는 공식 원문으로 승격하지 않는다. 자료의 현행성·법적 적용성은 이번 평가 대상이 아니다.

근거는 문서 ID와 **실제 본문의 인용 문자열**로 지정하며 필요하면 `heading_contains`로 절도 제한한다. 예를 들어 USCG의 International과 Inland 구분이 필요하다. 공백 차이는 정규화하지만 원문에 없는 인용·다른 문서·빈 라벨은 허용하지 않는다. 실제 `preprocess_sections()` 청크 중 근거 인용이 존재하는지도 실행 전에 검사한다.

평가셋의 `seed_hash_format: canonical-json-v1`과 `seed_sha256`은 JSON을 읽어 키를 정렬하고 공백 없는 UTF-8 표현으로 만든 내용 해시다. Windows CRLF와 Linux LF 또는 JSON 들여쓰기 차이는 허용하지만 문서 내용 변경은 거부한다. 결과 파일의 `provenance.sha256`은 별도로 실행 당시 파일 바이트 해시를 보존하므로 운영체제의 줄바꿈 차이에 따라 값이 다를 수 있다.

청크 ID는 재현용 `문서논리ID:청크순번`이다. 실제 DB의 개정 ID가 아니며, 기본 문서를 ID 순으로 정렬한다. DB 후보 정렬의 동점 순서나 권한별 corpus 차이를 검증하지 않는다.

작성자가 본문을 확인해 만든 초기 평가셋이다. 실제 선원 질문의 통계적 표본이나 독립 전문가 검수 완료본이 아니다. 팀원이 근거·질문의 명확성을 검토하고, 개발에 사용하지 않은 질문을 별도 보관한 뒤 개선 전후를 비교해야 한다. 결과를 높이려고 정답 라벨이나 검색 코드를 바꾸지 않는다.

현재 각 질문의 정답 근거 단위는 하나이므로 이 평가셋의 Hit@k와 Recall@k는 같다. 여러 근거가 모두 필요한 질문을 추가하면 둘이 달라질 수 있다. 평가 도구의 다중 근거 계산은 별도 단위 테스트로 확인한다.

## 지표 읽기

| 지표 | 의미와 분모 |
|---|---|
| Hit@k | 답 있는 질문 중 정답 근거를 하나 이상 찾은 질문 비율 |
| Recall@k | 질문별 정답 근거 단위 회수율의 평균. 같은 인용을 여러 청크가 포함해도 한 번만 센다 |
| MRR@k | 첫 정답 청크 순위의 역수 평균. 1위는 1, 2위는 0.5, 못 찾으면 0 |
| 답 없음 질문의 빈 결과 비율 | 답 없는 4개 질문 중 후보가 하나도 없는 비율. 답변 보류 정확도가 아니다 |
| first_retrieval_call | corpus 준비 후 첫 검색. 형태소 분석기·동의어 초기화를 포함할 수 있으며 프로세스 시작·파일 읽기·전처리 시간은 제외 |
| warm p50 / p95 | 초기 1회 이후 전체 질문×반복의 검색 시간 중앙값·95백분위수. DB·HTTP·LLM 시간은 제외 |

`--repeats 1`이면 질문별 시간은 단 한 번 측정한 값이다. 이때 p50/p95는 서로 다른 질문의 측정값 분포이며, 동일 질문 반복 안정성이나 통계적 신뢰 구간을 의미하지 않는다. 실제 운영 성능을 판단하려면 별도 장비에서 다른 부하를 통제하고 반복 측정해야 한다.

BM25는 일부 단어가 맞으면 답 없는 질문에도 후보를 반환할 수 있다. 예를 들어 “우리 선박 공식 CII 등급”에 일반 CII 설명이 잡히는 것 자체는 검색 버그나 LLM 환각을 뜻하지 않는다. 그 자료를 개별 선박 등급으로 오해하지 않는지는 API·LLM 별도 평가가 필요하다. 검색 점수도 신뢰 확률이 아니다.

## 후속 작업의 경계

- 이 작업으로 자유 질문 자동 라우팅·선박/기간 추출·추가 질문·대화 기억이 구현되지는 않는다.
- 권한은 운영 저장 계층의 기존 테스트로 검증한다. 이 도구는 로컬 기본 문서만 처리하고 운영 계정을 흉내 내지 않는다.
- 실제 로컬 LLM 품질과 전체 응답 시간은 질문별 기대 동작, 모델·장비·문서 corpus를 고정한 별도 평가가 필요하다.
- 검색 실패를 분석한 뒤 동의어·질문 표현·청크 분할·정답 라벨 문제를 구분한다. 알고리즘 변경은 이번 초기 기준선과 분리한다.
- 원문이 바뀌면 해시만 갱신하지 말고 모든 근거를 재검수한다. 질문/원문 경로는 `--cases`, `--seed`로 바꿀 수 있으나 동일 형식·해시 검사를 통과해야 한다.
