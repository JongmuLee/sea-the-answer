# 기존 CSV 버튼의 운항 자료 통합 등록

- 상태: 완료 (로컬·미제출, 원격 배포 제외)
- 작성: 2026-11-06
- 계약: [운항 자료 가져오기](../specs/operation-data-import.md)

기존 CSV 버튼에서 일별 운항 CSV, 준비된 MRV/Synthetic Noon CSV 묶음, DWT 후보 CSV와 AIS/항만 JSON을 판별하고 알맞은 기존 저장소에 등록한다. 임의 열/단위를 추측하지 않으며 알려진 준비 서식과 일별 서식을 지원한다. 반입 ZIP도 선택할 수 있어야 한다. 기존 작업·개인 DB·원격 저장소를 보존하며 PR/배포는 별도 요청 전 수행하지 않는다.

## 구현 결과

기존 운항 화면의 CSV 버튼과 모달을 확장했다. 사용자는 파일 선택 → 블록 전송 → 검증/미리보기 → 등록 순서로 같은 화면을 사용한다. 일별 운항과 연간 MRV를 별도 저장하며 준비된 출처·원본 선박·항차·Noon·품질·DWT와 AIS/항만 JSON을 함께 반입할 수 있다. 준비 스크립트의 서식과 DWT 검증을 backend 공통 모듈로 옮겨 CLI와 웹이 재사용한다. 새 의존성·migration은 없다.

관리자·CSRF·업로드 소유자·현재 계정 상태를 검사하고, 임시 용량·블록 순서·ZIP 경로·본문 해시·원본 식별자·유한한 음수 아닌 수량·DB 제약을 확인한다. 미리보기는 DB 롤백으로 영구 쓰기를 방지하며 등록 시 현재 자료를 재검사한다. 같은 행은 보존하고 다른 동일 키는 전체 DB 등록을 중단한다. 실제 앱 선박은 대량 생성하지 않으며 명시한 선택에 따라 유일한 기존 IMO 일치 선박만 연결한다.

DB 등록과 참조 JSON 설치의 성공 상태를 구분한다. 참조 연결 실패 뒤에는 DB를 다시 제출하지 않는다. 운영 볼륨의 참조 파일은 기존 파일을 보존한 뒤 원자적으로 교체하며 외부 지정 경로를 임의로 덮어쓰지 않는다. 자세한 계약은 [명세](../specs/operation-data-import.md), 화면 절차는 [사용 안내](../user-guide.md#3-운항-자료-csvzipjson)에 둔다.

### 실제 브라우저 등록 결과

반입 ZIP을 기존 CSV 버튼으로 선택해 출처 **6**, 원본 선박 **25,252**, MRV **80,552**, Synthetic Noon **4,380**, 가상 항차 **238**, 품질 **26,249**, DWT 후보 **25,240행**을 적재했다. 앱 일별 기록은 기존 **22행**을 유지했다. 앱 검증용 실제 선박 한 척만 별도로 등록하고 IMO 7422881을 기존 MRV 선박과 연결했다.

이후 원본 `annual_reports.csv` **86,395,506 bytes**를 같은 버튼으로 다시 전송했다. **동일 80,552행 / 신규 0행**을 미리보기와 등록 결과에서 확인했다. MRV 전체 행 MD5는 이전 작업과 동일한 **`47f6876da973fe710a15e0d2491caa1e`**였다.

AIS/항만 카탈로그는 고유 IMO **307척·2항구·53개 선석 그룹**의 준비 JSON이며 수집 시각을 보존한다. 관리형 Docker 볼륨에 설치한 뒤 backend를 재시작해 참조 조회와 기존 MRV 연결·계산을 다시 확인했다. 참조 SHA256은 **`98988792394010fd185345648c9b07c3927a5dc0a2b4ddcc595d6eff04809cd6`**다. 검증용 E2E tmpfs는 컨테이너 재생성 시 파일이 사라지므로 별도 override에서 운영처럼 named volume을 연결해 지속성을 검증했다.

실제 HTTP에서 미로그인 **401**, viewer **403**, 잘못된 CSRF **403**, 다른 관리자 소유 업로드 취소 **404**를 확인했다. 등록된 IMO 7422881의 2022년 MRV 참고 탄소집약도는 기존 Tool과 같은 **7.918235 gCO₂/(DWT t·nm)**이며 공식 CII·등급은 null이다. 최종 실행 backend 5개 핵심 파일 SHA256이 로컬과 일치했다 (`final-verification.json`).

## 한계와 인계

- 임의 CSV 열/단위 추론 기능이 아니다. 현재 준비 서식과 일별 서식을 지원하며 원시 MRV는 전처리한 뒤 반입한다. 처음 적재 시 부모 출처/선박/항차 자료도 필요하다.
- 웹 쓰기는 앱과 해사 데이터가 동일 PostgreSQL DB인 경우만 지원한다. 별도 해사 DB와 외부 읽기 전용 카탈로그는 기존 관리자 경로로 관리한다.
- 임시 업로드는 서버 프로세스에 묶이며 재시작 후 다시 선택한다. 20분 비활동 정리는 다음 업로드 요청에서 수행한다. 영구 DB·참조 볼륨과는 다르다.
- 운영 서버·개인 DB에는 이번 코드를 배포하거나 자료를 넣지 않았다. PR/push도 수행하지 않았다. 팀 웹 버튼에 반영하려면 코드 배포가 필요하다.
- 새로운 공식 CII 입력·실선 계측·실시간 AIS 수집·입항 승인을 확보한 작업은 아니다. 등록 후에도 기존 출처·노후화·참고값 경계를 따른다.

## 2026-11-08 PR #24의 백업 복구 E2E 경합 보완

상태: 재현·시험 보완 완료 (원격 전체 검증은 PR #24 Checks에서 확인). GitHub Actions run `42158251837`의 backend/frontend는 통과했고 E2E 28개 중 27개가 통과했다. 실패는 새 CSV 검사가 아니라 기존 백업 복구가 PostgreSQL 보호 잠금 때문에 `409 BUSY`를 받은 경우다. 자동 백업은 HTTP 요청 카운터와 별개로 같은 공유 잠금을 사용하므로, 복구의 첫 요청이 항상 성공한다는 시험 가정을 수정한다. 보호 잠금·복구 계약을 완화하지 않는다.

- [x] 실제 자동 백업을 진행 중 상태로 고정해 복구 거절·데이터/세션 보존·작업 완료 후 복구 성공을 재현한다.
- [x] E2E에서 같은 복구 확인을 `409 BUSY`일 때만 제한 시간 안에 재시도한다. 다른 오류는 즉시 실패시킨다.
- [x] 관련 backend와 전체 Docker E2E를 실행한다. 기존 PR 후속 커밋으로 제출하며 원격 결과는 PR Checks에 기록한다.

전용 PostgreSQL 18의 `test_fastapi_api.py`·`test_maritime_restore_links.py` **26 passed** (27.07초). 추가 시험은 실제 자동 백업 스레드를 멈춰 공유 잠금을 유지하고 HTTP 복구가 409로 거절되는 동안 데이터·세션·백업 파일이 보존되는지 확인한다. 스레드 해제 뒤 같은 HTTP 요청이 200으로 복구하고 세션이 무효화되는 것까지 검사한다. E2E에서는 첫 BUSY를 모의 응답으로 재현한 뒤 실제 복구 API가 성공해야 통과하며, 15초 내의 BUSY만 재시도한다. 실행 코드·보호 잠금·자동 백업 주기·인증·의존성·migration은 바꾸지 않는다. 증거는 git 제외 `output/pr24-backup-race-20261108/`에 보관한다.

이번 로컬 Docker 전체 실행은 **27 passed / 1 failed**다. 실패는 복구 이전의 `Question, real search, source dialog` 단계에서 `/api/ask` 응답을 60초 안에 받지 못한 경우이며, 복구 재시도 흐름에 도달하지 않았다. 이를 복구 성공 검증으로 계산하지 않고 제한 시간을 늘리지 않는다. 최종 전체 통과 여부는 같은 수정본의 [PR #24 GitHub 검사](https://github.com/dudco/sea-the-answer/pull/24/checks)로 확인한다. 전용 검증 환경만 종료하고 개인 DB·기존 볼륨은 유지했다.
